# PAY-ENV-03 — restricted DEV Stripe webhook hostname

Status: **DEV deployment and signed sandbox webhook ingestion verified 15 October 2026; end-to-end settlement not yet signed off**. This runbook records implemented DEV-only configuration and direct verification; no Production payment activation occurred.

## Why this design

The Admin Vercel project has Vercel Authentication with `ssoProtection.deploymentType = all_except_custom_domains`. **Do not infer a bypass for branch-linked custom domains from this setting.** Independent GitHub-hosted HTTP probes confirmed that this DEV Preview custom hostname returned HTTP `302` to `vercel.com/sso-api` on both ordinary GET requests and Stripe webhook POST requests. Stripe cannot log into Vercel. The fix was a Vercel **Protection Bypass for Automation** token attached as a secret query parameter in the **Stripe sandbox webhook endpoint configuration only**, as documented by Vercel for third-party webhooks. The bypass is project-level; treat its query token as a credential and never print, expose, commit or share the complete URL. No Admin Vercel Authentication was disabled.

Instead, the chosen name `dev-hooks.profilerelaunch.com` is a **single-purpose** webhook origin. The Admin Next.js `proxy.ts` guard checks the canonical request URL hostname first. With the Vercel automation bypass present, this hostname's `proxy.ts` guard is intended to forward **only** `POST /api/webhooks/stripe` **and only when** `VERCEL_ENV=preview`; all other paths and methods must return 404 with no-store headers. These negative cases are covered in proxy unit tests but are **not yet independently proven through the public bypass URL**. Without the bypass, the Vercel SSO layer instead redirects every route. Production Admin and normal Preview URLs remain protected.

The handler still requires a configured sandbox provider, `whsec_` signature verification of the raw body, exact `livemode=false` and the DEV database lane; the database ensures idempotency. The guard is not a substitute for those checks. No Stripe activation occurs merely by routing an endpoint.

## Reversal

Before Stripe configuration, removing the Vercel `dev-hooks` domain assignment and the **specific** Cloudflare `dev-hooks` record restores the prior network surface; do not affect existing production records. If a sandbox secret has been issued, first disable the sandbox endpoint and `PAYMENTS_PROVIDER_MODE` on Admin/Customer Preview, redeploy and revoke the endpoint's sandbox signing secret as appropriate. The `proxy.ts` host guard is safe to retain. An environment-variable rollback stops new calls; it does not reverse transactions already made.

## Security and rollback note

A Vercel automation-bypass query token grants broader project-level Preview access than just this single endpoint, so protect the Stripe dashboard configuration and never put its full URL into GitHub/CI/logs. Stripe's independent `whsec_` signature verification is mandatory and remains enabled. If the automation token is compromised, rotate it through Vercel and update the Stripe sandbox endpoint atomically; previously issued bypasses should be revoked. If relocating to a dedicated webhook-only project becomes justified, reevaluate costs and the host-only guard before reducing SSO protection anywhere else.
