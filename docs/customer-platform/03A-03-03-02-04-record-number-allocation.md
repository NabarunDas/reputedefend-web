`public.admin_commercial_record_number_allocation_v1(text, uuid, uuid, integer, jsonb)` records one existing telephone allocation for one selected Telloya location. It runs only after Begin Setup, confirmed preferences for every selected location, and a current AI configuration for that location. It is service-role only. The Admin route also requires `ADMIN_COMMERCIAL_SETUP_QUEUE_ENABLED` and `ADMIN_COMMERCIAL_RECORD_NUMBER_ALLOCATION_ENABLED`. Both default off. The database does not read either flag.

The provider environment is the server lane from `VERCEL_ENV`. A browser-supplied environment that differs is rejected before the database call. The database still checks that the submitted environment matches the latest configuration.

One E.164 number has one owner in this database, paired with the exact configured agent. The owner key is the provider and the number. It does not include the environment, so the same number cannot be reserved for DEV and Production in this database, or for two customers, businesses, or locations. The assigned agent does not change without a future audited release. The ownership lock is taken before the ownership read. An inactive `telloya_voice_number_bindings` row does not release the number. An active routing row blocks the allocation. This command does not insert or activate a routing binding. A separate Supabase database is not covered by this constraint.

`OPERATOR_ATTESTED` means a staff member recorded provider evidence. It is not an independent provider check and it does not show that the number is routing calls.

A first successful record sets `number_allocated_at`, stores `provider_binding_ref` as `alloc:` plus that allocation id, and moves that provision from `NUMBER_REQUIRED` to `FORWARDING_REQUIRED`. It does not set forwarding, test-call, customer confirmation, or live timestamps, and it does not set `LIVE`. The telephone checklist stays planned until forwarding is recorded. A later correction by the same owner appends history, keeps the original `number_allocated_at`, and moves `provider_binding_ref` to the new allocation id. The provision stays `FORWARDING_REQUIRED`. A correction is refused once forwarding, testing, customer confirmation, or activation evidence exists. A replaced number stays owned. `admin_private.commercial_authoritative_allocation_id_v1` returns only the allocation named by the current provision reference when that row is the latest allocation for the location. Future forwarding commands must use that id.

Inserts and updates of `public.telloya_voice_number_bindings` check commercial number and agent ownership inside PostgreSQL. A reserved number must use its stored agent and the same provider environment, business, and location, and the row must stay inactive. `active = true` is rejected for a reserved number, including an update of a matching inactive row and `telloya_voice_bind_number_v1`. A commercially owned agent must match that environment, business, and location. A binding with no commercial reservation keeps the existing voice rules. A future activation command must bring its own audited authorisation. This phase still does not create a routing binding.

The Customer Portal says the number has been recorded and that forwarding instructions are being prepared. It does not show provider references, staff attestation, or the telephone number, and it does not say forwarding is ready.
