# Evidence SHA-256 integrity

SEC-08 lets a trusted server compare evidence bytes in private S3 with SHA-256 metadata in `public.case_document_versions`. The migration is source-only. Do not apply it to DEV or Production from the pull request that adds it, and do not move `ApprovedMigrationHead`.

## What is trusted

The Admin server computes SHA-256 from the bytes returned by `GetObject`, and only after the live GuardDuty tag is `NO_THREATS_FOUND`, the byte length equals `declared_size_bytes`, and the existing magic-byte check passes. `public.evidence_content_sha256_v1` then stores that digest if the row has none.

A browser digest is rejected. An S3 entity tag is not a SHA-256 of the object. Customer upload and Customer finalize do not hash the file. Admin finalize only checks that the object tag can be read.

## Staged rollout

Existing `VALID` rows may have a null digest. They stay valid, so prepared packs and downloads do not become stale only because the hash is missing. A new transition to `VALID` through `admin_evidence_refresh_scan_v1` requires a digest already stored for that version. The first successful Admin refresh of a clean legacy file records the digest and can remain `VALID`. A later refresh whose bytes disagree is `INVALID` and does not replace the stored digest.

The migration adds nullable columns and does not update existing rows. Rollback is a later reviewed migration. Do not edit this file after it has been applied.

## Backfill

`scripts/evidence-sha256.mjs` is run by an operator. It is not a cron and it is not part of CI.

```
node --experimental-strip-types scripts/evidence-sha256.mjs --mode check
node --experimental-strip-types scripts/evidence-sha256.mjs --mode apply --limit 50
node --experimental-strip-types scripts/evidence-sha256.mjs --mode apply --after <version-id>
```

`check` is the default. It writes nothing. `apply` records a digest only where none is stored, and only when `AWS_EVIDENCE_BUCKET` is the DEV bucket, `VERCEL_ENV` is not `production`, and `SUPABASE_URL` is not the Production project. A second apply reports `already_trusted` and does not change `content_sha256_verified_at`. Static AWS keys are refused.

`--after` is the last completed version id. Use it to resume an interrupted run. Exit 1 means a failed object. Exit 3 means the limit stopped the run before the end. Exit 2 means the command was refused.

## Restore verification

After metadata is restored, run the same script in `restore` mode against the recovered database and the recovered bucket. `restore` is read-only, including for Production.

```
node --experimental-strip-types scripts/evidence-sha256.mjs --mode restore
```

| Outcome | Meaning |
| --- | --- |
| `match` | Recovered bytes match the recorded SHA-256 and the declared size |
| `mismatch` | The object is present and its bytes differ from the recorded digest |
| `missing` | The object is not in the bucket |
| `size_mismatch` | The object length differs from `declared_size_bytes` |
| `unverified` | The object is present and clean, and no digest has been recorded yet |
| `unreadable` | The object could not be read, including an access denial |
| `not_clean` | The live GuardDuty tag is not `NO_THREATS_FOUND`, so the bytes were not read |
| `bucket_mismatch` | The row names a different bucket, so the object was not read |

The output is version id, outcome and sizes. It does not include filenames, object keys, digests or file bytes. `unverified` is not byte-level proof. The existing recovery report treats a null checksum the same way: `checksum_unavailable` and `byteIntegrityProven: false`.

## What this does not guarantee

A presigned POST does not deny overwrite and does not bind a checksum. Until it expires, it can replace the object. After that, any principal with `s3:PutObject` on `cases/*` can replace the latest object. Production versioning may keep older versions, but this application does not store an S3 VersionId and reads the latest object. Verification detects a replacement on the next hash comparison. It does not prevent one.

View and Download still use a short-lived presigned GET. They do not download the object through Vercel to hash it again. A replacement made after the digest was stored remains downloadable until a refresh or a restore check marks it invalid.

The `service_role` key can call the record function. That is the existing server trust boundary. The browser cannot.

## Cost and AWS

Each candidate costs one `GetObjectTagging` and, when the tag is clean, one `GetObject` of at most 10 MB. `apply` reads only rows with no digest. `check` and `restore` read every clean uploaded row in the page. There is no new bucket, index, background worker, or stored copy of the file.

No IAM change is required when the Admin evidence role used for validation already allows `s3:GetObject` and `s3:GetObjectTagging`. The script uses that role through Vercel OIDC and never writes an object. The Customer role is not used. Do not add `DeleteObject`, `PutObject`, or a broader prefix for this task. Do not change bucket versioning, Object Lock, CORS, or retention here.
